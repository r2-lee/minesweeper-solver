# 扫雷自动计算：算法改进全记录

这份文档记录了自动计算求解器从「能跑」到「和最好的开源求解器打平手差 1.3 个点」的全过程：
每一次尝试、每一个数字、每一次被证伪的想法，以及为什么最后停在现在这个实现上。

数据都可以用仓库里的工具复现，命令见文末附录。

---

## 1. 一句话结论

**胜率已进入公开开源求解器的第一梯队，但没有超过 EdLogg 的 `MineSweeper`。**

| 口径（高级 30×16 / 99 雷，首点 (3,3)，seed 2026，5000 局） | 胜率 | 猜测次数/局 |
|---|---|---|
| EdLogg `MineSweeper`（C++，原样编译） | **52.50%** | 2.25 |
| 本仓库 | **51.22%** | 2.73 |
| 差 | **−1.28 点**（McNemar z = 2.16，p ≈ 0.03） | +0.48 |

差距**不在概率模型**：我们的边际概率在可达局面下就是完整约束系统（含总雷数）的精确后验
（152 个局面 / 814 格逐格与暴力枚举一致，0 处不符），0/1 判定零错判。
差距也不在「选哪一格」：11 种猜法全部测过，没有一种在 2000 局尺度上超过「挑最安全的格」。
差距主要在**每局要多猜 0.5 次左右**，而这 0.5 次来自「整局的猜测序列规划」，不是任何单步启发式能解决的。

## 2. 对照基准怎么建的（这一段很重要）

### 2.1 为什么要拿 EdLogg 当基准

高级难度的公开数据：

| 来源 | 胜率 | 口径 |
|---|---|---|
| [DavidNHill/JSMinesweeper](https://github.com/DavidNHill/JSMinesweeper)（Java） | **54.3%** | modern expert，首点开一片 |
| 同上，classic expert（首点在角落） | 41% | 首点只保证不炸 |
| [EdLogg/MineSweeper](https://github.com/EdLogg/MineSweeper) | **53.96%** | modern expert，20 万局 |
| [MinesweeperHQ 模拟](https://minesweeperhq.com/minesweeper-odds/) | 50.7% | 首点及 8 邻域保证无雷，10 万局 |
| [大森/井上 2012](https://cir.nii.ac.jp/crid/1571135652847110912) | 49.4% | 全文枚举 + 最小概率 |
| [gamescomputersplay/minesweeper-solver](https://github.com/gamescomputersplay/minesweeper-solver) | 38.6±0.3% | 自带 bot，2D expert |
| [henrlly/minesweeper-solver](https://github.com/henrlly/minesweeper-solver) | 38.0% | 确定性求解 |

EdLogg 的仓库既有生成器又有求解器，可以做到「同一批棋盘」比较，所以选它做基准。

### 2.2 把他的求解器原样编译出来

`tank.cpp` / `fastSolve.cpp` / `hash.cpp` / `game.cpp` 没有 GUI 依赖，只有 `MineSweeper.cpp`
（MFC 界面）里定义了一批全局量。于是补一个 `globals.cpp` 提供这些全局量，写一个
`driver.cpp` 提供控制台入口，用 cl 直接编成 `ed.exe`：

```
cl /O2 /EHsc /D_CRT_SECURE_NO_WARNINGS /DNDEBUG driver.cpp globals.cpp game.cpp tank.cpp ^
   fastSolve.cpp hash.cpp rand.cpp file.cpp /Fe:ed.exe ^
   /link user32.lib comdlg32.lib ole32.lib shell32.lib
```

踩过的坑：

1. 他的源码是 GBK + 中文注释，我加的 `globals.cpp` 必须纯 ASCII，否则 C2146/C2065。
2. 他的求解器**不可重入**：一个进程连跑 300 局会在第 156 局访问违规（`0xC0000005`）。
   解决办法是「每局一个进程」。
3. `bestx/besty` 在 `MakeMove` 返回前就被清成 -1，所以坐标只能靠 `Expose`/`AddMine` 埋钩子记录。
4. `AddMine` 不只在真标雷时调用（`tank.cpp:1509/1526` 的推断路径也调），
   平均每局约 560 次、70% 落在安全格 —— 这直接决定了「不能拿 `AddMine` 重放状态」。

复现结果：seed 1、5000 局、每局独立进程 → **2659 胜 = 53.18%**（他 README 公布的 53.37%，
n = 10000），`guesses/game = 2.27`。**确认复现成功。**

### 2.3 状态级插桩（后来所有对比的基础）

在 `driver.cpp` 里每个 `MakeMove()` 前后各快照一次他内部的 `exposed[][]`，只打印真实变化：

```
d <x> <y> <before> <after>     # 9 = 雷，0..8 = 数字
s <step> <rule> <guesses> <prob> <remaining> <calls>
end <result> <guesses> <prob> <remaining>
<rows 行雷图>
```

把 `d` 行应用到我们自己的 `Board`（9 → `mark_mine`，0..8 → `Mark.OPENED`），
再逐格比较「我们算出来的数字」和他的 `exposed` 值：**44610 格，0 处不符**
（把我们的空区 `-10` 归一成 `0` 后）。从此他的每一个决策时刻我们都能精确复现。

### 2.4 棋盘来源的分歧（一次真实的翻车）

早期我们用自己重写的发牌器（KISS + `NewGame`，已对拍逐位一致）生成棋盘，
得到「我们 50.45% vs 他 53.18%」。后来发现：**单盘 seed 1 相同，但成批之后种子链分叉**。

同代码只换棋盘来源：

| 棋盘来源 | 我们的胜率 |
|---|---|
| `edlogg_layouts`（我们重写的发牌器），500 盘 | 50.40% |
| 他的 `trace` 导出的 `end` 雷图，1000 盘 | 51.50% |

所以「50.45% vs 53.18%」是跨棋盘比较，**作废**。之后统一成「以我们的发牌器为准，
把同一张雷图喂进他的 `edl.exe`」：

```
edl.exe <layout-file>    # 首行 rows cols mines sx sy，随后 rows 行 0/1 字符串
```

## 3. 求解器现状（拓扑与性能）

```
UI (PyQt5)  ──►  Board (core)  ──►  AutoSolver (solver/strategy.py)
                                      │
                    ┌─────────────────┼──────────────────┐
                    ▼                 ▼                  ▼
          frontier.py（精确边际）   endgame.py（端局）   guess.py（猜法）
                    │                 │                  │
              accelerator.py ──► frontier_native.pyd（C++ 枚举器）
```

- **确定性层**：`RULE_1/2` 式必然手（`_certain_actions`），加精确边际给出的 0/1 格。
- **精确边际**（`frontier.py`）：每个数字格一条约束 → 并查集切成连通组件 → 组件内 DFS 枚举
  `ways[k]` / `cell_ways[cell][k]` → 组件间按雷数卷积 → 与空白格 `C(free, rest)` 合并
  → 得到全盘每一格的精确边际概率。全整数运算，最后才转 float。
- **原生枚举器**（`native/frontier_native.cpp`）：只替换最热的组件枚举。与纯 Python 逐位一致
  （300 张随机棋盘 / 569 个组件），最坏单组件 15.7 s → 0.06 s。
- **端局**（`endgame.py`）：未知格 ≤ 20、雷图 ≤ 512 时做信念集合上的期望最大搜索。
- **猜法**（`guess.py` / `lookahead.py` / `gametree.py` / `rollout.py` / `planner.py`）：
  默认 `min_prob`（挑边际概率最低的格），其余全部是可选开关。

速度（高级，2000 局，Linux 16 进程，原生加速器）：**2.8 s**（约 1.4 ms/局·每步）。
重构前是 48 s，做了两轮优化（PERF-10）后快了 17 倍；单进程 400 局 58.1 s → 25.8 s（2.25×）。

## 4. 已修复的算法缺陷

这些是「行为上确实会错」的缺陷，不是风格问题。全部有回归测试。

| 编号 | 症状 | 修法 |
|---|---|---|
| KI-1 | 原生枚举返回 `count = -1`（表示「算不了」）被当成有效结果 → `abs(acc/-1) = 0` → 在窗口左上角造出「必然安全」的假信号 | `local.py` 改判 `count <= 0` → 空表 |
| KI-2 | 中心数字减周围已标雷数可能为负 → 传给原生 `min_x` 触发 C++ 越界 | 入口检查 `min_mines < 0` 直接放弃 |
| KI-3 | 全局枚举的 `k = remain_mine()` 可能大于未开格数 → C++ 越界 | 入口检查 `0 <= remain <= len(unknown)` |
| KI-4 | 窗口切片的谓词上界用 `rows + 1`、切片用 `rows` → 贴边整行/列被排除 | `_in_window(coord, start, stop, size)` 统一用 `size - 1` |
| KI-5 | 一维化时缺 `i >= 0` 检查 → Python 负下标回绕 | 过滤 `0 <= i - top < ax` |
| KI-6 | `trim_zero_edges` 连续两行全 0 会一起裁掉 | **保留**（只影响窗口法，已不是默认路径） |
| KI-7 | `max_mines` 只累加「八邻域完整落在窗内」的数字格 → 边界数字格旁边的雷被漏算 → 真雷报成 0.0 | `max_mines = min(候选格数, 所有数字之和 + 完全不受约束的候选格数)` |
| PERF-1 | 相邻数字格把同一批未开格各算一遍 → 对同一格重复展开/标雷空转 | 输出动作前查 `mark_matrix`，已开/已标则跳过（高级一局 925 → 241 步） |

KI-7 是其中最值钱的一个：它修完之前，100 局里有 1 次「按概率表 0.0 打开结果踩雷」，
修完后 2000 局 0 次。

## 5. 十四个机制，十四次 A/B

统一口径：高级 30×16/99，seed 2026（或 EdLogg 盘 seed 1–5 各 400），n ≥ 1000，Linux 16 进程。
基线 **`min_prob` = 50.45%**（1009/2000，2.8 s）。样本量 2000 时的标准误约 1.1 点，
所以「+0.3 点」这种量级全部是噪声。

| # | 机制 | 想法 | 结果 | 结论 |
|---|---|---|---|---|
| PERF-2 | 一步前瞻（lookahead） | 算「打开这一格能连带解开多少」 | 48.5% / 49.0%（慢 4–6×） | 更差 |
| PERF-3 | 端局精确搜索（endgame） | 未知格少时穷举所有雷图的期望最大 | 49.80% vs 49.40% | 噪声，留着（不亏） |
| PERF-4 | JSMinesweeper 式「进度 + 两拍存活率」 | 先看下一手能不能出现 100% 安全动作 | 49.80% | 噪声 |
| PERF-5 | 边沿加权期望搜索（search） | 世界 = 边沿配置 + `C(free, rest)` 权重，深度可调 | d2 50.35 / d3 50.20 / d8 50.20 | 更差，且深度越大越慢 |
| PERF-6 | rollout | 真下几局看胜率 | 49.90%（3 样本）/ 50.00%（12 样本） | 噪声，慢 3–11× |
| PERF-7 | 少猜优先（fewest） | 数「打开后还剩几块必须猜」 | 50.75%（猜测 2.688 → 2.643） | 噪声；88% 的评估因组件过大失效 |
| PERF-8 | 超级位置（superloc） | 照 EdLogg：用略高的雷概率换炸开一片 | 50.40% / 50.20% / 47.80% | 在他那里成立，搬过来不成立 |
| PERF-9 | 完整期望搜索（gametree）+ 直跳空白区（blank） | 不截断的期望最大；直接点空区 | 50.85% / **40.90%** | gametree 噪声，blank 崩盘 |
| PERF-10 | 速度优化 | `is_won` 逐行统计、内联八邻域、`comb` 记忆化、复用 `values` | 58.1 s → 25.8 s（400 局） | **胜率逐局不变** |
| PERF-11 | 逐决策重放对比 | 把他的每步重放到我们的盘上比风险 | — | **结论撤回**：`AddMine` 有 70% 落在安全格，重放状态不可信 |
| PERF-12 | gamble | 边沿 vs 空区各 rollout 一批，严格更优才改选 | 50.40% | 噪声 |
| PERF-13 | 动作粒度 | 学它「一个动作开一批」 | 只做了度量 | 见 §7 |
| PERF-14 | pinned | 对「被总雷数钉死」的组件单独做期望搜索 | **46.00%** | 明显更差（把「解开组件」当收益会高估） |
| — | UCT 规划器（planner） | 信念空间里 UCB1 选动作，奖励是整局胜负 | 50.85%（慢 10×） | 噪声，且与 gametree 同为 1017/2000 |
| — | deep 并列 | 概率并列时选未知邻格最多者 | 50.50%（慢 2.7×） | 噪声 |
| — | 宽端局 | 端局门槛 20/512/2000 → 40/4096/20000 | 50.50%（慢 7.8×） | 噪声；端局只改「猜哪格」，不改「要不要猜」 |

**十四种机制，没有一种在 2000 局尺度上超过基线。** 这不是实现不认真的问题：
每一种都有对应的单元测试（229 个用例），也都有日志确认它真的被触发过
（例：superloc 在 120 局里被调用 247 次、改变选择 79 次；fewest 在 88% 的决策上退化成基线）。
这是「单步启发式已经吃到头」的典型形态。

## 6. 三个关键验证（说明差距不在哪里）

### 6.1 精确边际的正确性（方案二）

用三层验证：

1. **与暴力枚举对拍**：400 个随机 4–5×5 棋盘，逐格与 `itertools.combinations` 枚举的
   真实后验比较，0 处不一致。
2. **可达局面全量对拍**：152 个「用 `expansion` 造出来的真实局面」/ 814 格，0 处不一致
   （`tests/test_frontier.py::ReachableExactnessTest`）。
3. **与全局闭包比较**：EdLogg 的 `ForceMine`/`ForceExpose` 只在单个周长列表内部推导，
   推出来的每一格我们的精确表必然也有 → **他的确定性集合是我们的子集**，
   移植他的约束传播不会多挖出一格。

顺带记两次探针翻车（教训）：`frontier.probabilities()` 要的是 `ConstraintSystem` 不是 `Board`，
传错会**静默返回空表**而不是报错；以及手工置 `Mark.OPENED` 会造出「数字为 0 的已开格旁边
还盖着牌」这种**不可达局面**（真实对局 `flood_open` 会一起翻开），此时 `build_system`
不为 0 格的邻居建约束是**正确**的，却被我当成了 bug。

### 6.2 概率标定（100 局 / 273 次真实猜测）

| 预测概率 | 实际踩雷率 | 样本 |
|---|---|---|
| ~0.0 | 0.050 | 20 |
| ~0.1 | 0.110 | 146 |
| ~0.2 | 0.250 | 52 |
| ~0.3 | 0.250 | 8 |
| 0.4–0.5 | 0.489 | 47 |

总体：预测均值 0.1841，实际 0.2015（偏差 9%，n = 273 的标准误约 2.4%）。
**概率不是算错，只是这个样本的波动。**

### 6.3 退化率（`FrontierTooLarge`）

300 局、6077 次精确求解：`too_large = 0`。装了原生加速器后预算放到 2000 万节点，
统计上**不会退化**（纯 Python 版本 2000 局 0.6% 的局会退化到窗口法，装了原生后 0 次）。

## 7. 差距到底在哪：共识是「猜测次数」

| | 我们 | EdLogg |
|---|---|---|
| 胜率（同一批发牌器，5000 局） | 51.22% | 52.50% |
| 猜测次数/局（他自己的计数） | 2.73 | 2.25 |
| 猜测次数/局（用我们的精确表当裁判） | 2.61 | 1.71 |
| 每次猜测的平均格雷概率 | 0.193 | 0.22 |
| 每局动作数（只看胜局） | 311.7 | 221.8 |
| 每次动作揭开的格数 | 1.23 | 1.57 |
| 一次动作揭开多格的步占比 | 4% | **22%** |

把胜率拆成 `P ≈ q^n`：

- 我们 `0.774^2.69 ≈ 0.504`
- 他 `0.766^2.35 ≈ 0.532`

**两边每一步的冒险程度几乎相同，差的是「要冒几次险」。** 他的 `q` 甚至略低一点
（因为他会为了开大片而冒更大的风险），但次数少 0.3–0.5 次。

动作粒度（PERF-13）是目前发现的唯一「结构性」差异：他的 `MakeMove()` 里
`RULE_2` 是「一个数字周围的雷标全了，就把剩下的邻格**一次全开**」，一个动作开一批；
我们是一个 `Action` 开一格。这会让他「清完一个数字」的动作数少 4–5 倍。
但这只是**动作粒度**，理论上不改变胜率（同一格踩雷还是踩雷），
我们实测也没找到把它转成胜率的机制。

## 8. 参考：另一个开源项目怎么做的

用户提到的「性能接近」的项目，最可能就是 **David Hill 的
[JSMinesweeper](https://github.com/DavidNHill/JSMinesweeper)**（Java / JS，modern expert 54.3%）。
顺带一提：EdLogg 在 README 里明确写了他的想法来自 David Hill（Reddit `BinaryChop`），
所以这两个项目的算法是同一族的。

它的求解器分五层，**从便宜到贵依次尝试，前面有结果就不往后走**
（[README](https://github.com/DavidNHill/JSMinesweeper/blob/master/README.md)、
[wiki: 术语](https://github-wiki-see.page/m/DavidNHill/Minesweeper/wiki/Terminology)、
[wiki: brute force deep analysis](https://github-wiki-see.page/m/DavidNHill/Minesweeper/wiki/Brute-force-deep-analysis)）：

1. **Trivial analysis** — 等价于我们的 `RULE_1/RULE_2`（数字周围未开格数 == 数字 → 全标雷；
   雷标全 → 剩余邻格全开），循环到不动点。
2. **Probability engine** — 把约束拆成互相独立的「子集」，每个子集枚举所有解，
   再用**全盘剩余雷数**把子集的解组合起来算概率。等价于我们的 `frontier.py`
   （组件分解 + 总雷数卷积），只是他们是边算边拆、我们是先建全盘约束系统再拆。
3. **50/50 与伪 50/50 检测** — 识别「两格共享一颗雷且永远不会被分开」的结构，
   尽早把这种必然硬币点掉。**我们没做这个**：我们的精确表当然知道那两格是 0.5/0.5，
   但我们没有「这枚硬币永远无法通过后续信息解开」的判定，所以不会优先点它。
4. **Guessing logic** — 候选限制在「最安全格 10% 带宽内」，对每个候选算
   *progress*（下一手能否出现 100% 安全的动作）和 *secondary safety*（连这一手和下一手
   都活下来的概率），混合打分。≈ 我们的 `choose_open_progress`（PERF-4）。
5. **Brute force analysis / deep analysis** — 候选解少于 4000 时，真的把
   「每个格子 × 每种顺序」推演一遍，算精确胜率。≈ 我们的 `endgame.py` / `gametree.py`。
   它的 wiki 里有个我们没实现的关键概念：**living tile** ——
   「未开、且可能有多个取值的格」；点 non-living 格既不会死也不会带来新信息，
   所以平局时优先点 living 的格。如果一盘棋已经没有 living tile，
   胜率就等于 `1 / 候选解个数`（纯抽奖）。

对我们有借鉴意义、且**还没做**的两条：

- **50/50 检测**：把「永远解不开的硬币」提前点掉，可以让后续的确定性推理早一点开始
  （我们的做法是拖到最后，可能因此多花了几步）。
- **living tile 判据**：我们的 `deep`（并列时选未知邻格最多）只是它的粗糙近似；
  严格版本应该是「这个格子的取值在候选解集合里是否唯一」。

另外两个性能量级更低、但实现清晰可参考的：

（C++/WASM，38.6%，有完整的模拟测试框架）、
[henrlly/minesweeper-solver](https://github.com/henrlly/minesweeper-solver)
（38.0%，CSP + 暴力搜索）。

## 9. 方法论上的教训（写给未来的自己）

1. **n ≥ 1000 才有结论**。同一配置的 100 局分块能在 94/92/94/96/97/97/98/95/96/97 之间跳，
   单块波动 ±3 点；200 局比较「+0.3 点」等于抛硬币。
2. **口径必须一致**。跨棋盘比较（他的发牌器 vs 我们的发牌器）直接导致过一次 3 点的假结论。
3. **monkeypatch 要打在真正使用该名字的模块上**。`strategy.py` 用
   `from .guess import choose_open` 绑定了自己的引用，patch `guess.choose_open` 无效
   （表现为「统计到 0 次」）。
4. **探针本身要先验证**。两次「645/645 全错」不是求解器的错，是我构造了不可达局面；
   `probabilities()` 传错类型会静默返回空表。现在的习惯是：先断言表非空、再断言两边
   布局总数一致、最后才比逐格。
5. **别用「能开多少格」当收益的代理**。progress / 面积 / 区域大小这一类指标全部失败，
   因为它们和「整局还剩几次猜」不是单调关系。真正的目标函数是胜率，只能 rollout 或搜索去估，
   而 rollout 的方差又大得吃掉了差异。

2. **整局规划**：以「整局还要猜几次」为目标的信念集合递归 DP。`planner.py` 是第一版

## 附录 B：EdLogg 求解器逐层拆解

按 `MakeMove()` 的规则顺序（`tank.cpp`）：

1. **`RULE_1` / `RULE_2` / `DEDUCE`** —— 最基础的必然手。
   - `RULE_1`：某数字周围未开格数 == 数字 → 全部标雷。
   - `RULE_2`：某数字周围的雷已标全 → 剩余邻格一次全开。
   - `DEDUCE`：贪心/去重，避免重复动作。
   - 三者循环到不动点，一局平均 110.1 / 72.7 / 14.7 次。≈ 我们的 `_certain_actions`。

2. **周长建模** —— `CreatePerimeterLists` 把「与数字相邻的未开格」按共享约束连成 list
   （≈ 我们的并查集组件），`CreateSolutions` 做 DFS 枚举，`CalculateProb` 用
   `CountSolutions` / `CountWeightedSolutions` 按**总剩余雷数**做组合加权算概率。
   ≈ 我们的 `frontier.py`（组件分解 + 总雷数卷积），已逐位对拍。

3. **猜法层**（按优先级）：
   - `GUESS_0`：最低概率 + 横竖「guess 0」模式（≈ 我们的 `min_prob`），0.36 次/局。
   - `SUPERLOC`（`FindSuperLocations` / `UseSuperLoc`）：**不在边沿上的空白格**，
     用 `exposed = 1 - nonPerimeterProb + count * openProb[count+1]` 打分，
     1.18 次/局、该步存活率 0.883。他会为了「炸开一片」主动多冒一点险。
   - `GAMETREE`：解数 < `maxSolutions` 时对候选方案做期望最大搜索，0.38 次/局。
   - `GUESS_1` / `GUESS_2`：概率未知时的兜底，0.10 / 0.33 次/局。

4. **端局**：`fastSolve.cpp` 的暴力求解 + `FindEasySolution` + `hash.cpp` 记忆化；
   门控是 `remainingCount + mineCount <= END_PLAY_COUNT(64)` 且 `totalSolutions <= maxSolutions`。

### 关键实验：关掉他的 gametree

用 `ED_MAXSOL=0` 让 `UseGameTree` 直接早退（gametree 与端局暴力一起关）：

| | 胜率 | 猜测/局 |
|---|---|---|
| 默认 | 53.75% | 2.24 |
| `ED_MAXSOL=0` | **54.00%** | 2.29 |

→ **他自己的 game tree / 端局暴力对胜率的贡献约等于 0**（甚至略负）。
这也解释了为什么我们照着实现的 `endgame.py` / `gametree.py` 同样是噪声内。
他真正的优势是「整局只猜 2.25 次」，而这来自前面三层确定性推理的覆盖率，
不是最后那层搜索。


## 11. PERF-15：50/50 提前点掉与 living tile（JSMinesweeper 的最后两条）

JSMinesweeper 的 wiki 里还有两条我们没做的：把"必然 50/50"的对子尽早点掉、平局时优先点 living tile。两条都实现了，**都没有收益**，而且"提前点掉硬币"这件事本身是负收益。

实现：`guess.find_coin`（组件内枚举配置，要求两格 XOR 恒为真**且**两格概率都恰好 0.5）与 `guess.choose_open_living`（抽 24 张后验雷图，选"打开后能看到最多不同数字"的那格）。

| 策略 | 胜率 (n=400) | 耗时 |
| --- | --- | --- |
| `min_prob`（默认） | **50.0%** | 4.2 s |
| `living` | 47.25% | 21.1 s |
| `coin`（残局前也点） | 30.5% | 3.7 s |

`coin` 的阈值扫描（`coin_cells` = 允许提前点硬币时"未知格 ≤ N"，N 越小越晚）：

| coin_cells | 30 | 20 | 14 | 10 | 6 |
| --- | --- | --- | --- | --- | --- |
| 胜率 (n=400) | 30.50% | 37.50% | 42.50% | 44.25% | **48.75%** |

单调曲线说明问题在**时机**不在检测：只要等到"硬币已经到了残局"（N≤6）才点，胜率就回到基线；越提前越亏。

机制：p=0.5 只对"当前约束"成立。以后翻开的格子会往系统里加约束（尤其是贴着这格的未知数字），很多对子本来会被后来的信息**免费解开**（某一格变成 1.0、另一格变成 0.0）。提前点掉等于把"可以等出确定性"的局面提前兑现成 50%，而活下来的那一半还要接着打完整局。所以 `min_prob` 不点它、先去吃 0.02~0.15 的安全格，恰恰是对的。

实现里踩到的两个坑也值得记录：① 只判"两格 XOR 恒真"会把"一格恒雷 + 一格恒安全"当成硬币（点了必死），必须先要求两格各占一半配置；② 权重不同时 XOR 仍成立（实测 0.878/0.122），所以最后还要用精确边际二次确认两格都是 0.5。第一版没做这两步，200 局只赢了 1 局。

结论：这两条也不进默认策略（`guess_policy` 仍为 `min_prob`），代码留作可选项与后续实验的起点。


## 12. PERF-16 同风险候选的精确分支加权（2026-11-18）

## PERF-17：progress 猜法的两处提速（胜率不变）

`progress` 的预算是"每个候选跑若干次续局、每次续局打到终局"。剖析 4 局（cProfile，5.95 s）显示
5.70 s 都在 `choose_open_progress` 里：`rollout.simulate` 159 次占 5.33 s，其中 **`endgame.solve`
被调用 370 次、占 3.00 s**——续局里每一步猜又嵌套了一次端局精确搜索。

两处改动：

1. **续局不再嵌套端局搜索**。`choose_open_progress` 原来给续局构造裸 `SolverConfig()`（`endgame=True`），
   现在默认 `endgame=False`（用 `rollout._rollout_config()`），需要时用
   `SolverConfig.progress_endgame=True` 打开。3 000 局同盘：关 **1502/3000 = 50.07%**、273.8 s；
   开 1499/3000 = 49.97%、417.5 s → **胜率等价（+3 局，噪声），快 34%**。
2. **约束系统增量维护**。`frontier.IncrementalBuilder` 保存 `mark_matrix` 快照，只重算"变动的格子及其
   八邻域数字格"的约束，其余复用；语义与 `build_system` 完全一致（约束按行列序输出，frontier/free
   顺序相同）。1 114 步逐步比对 `constraints/frontier/free/total_mines`，**0 处不一致**；
   3 000 局胜场与改动前**逐局相同**（1502），耗时 273.8 s → 228.9 s。

合计：4 局续局基准 5.12 s → 1.74 s（约 2.9×）；3 000 局整局基准 273.8 s → 228.9 s。
同一批盘上 `min_prob` 3 000 局为 1484/3000 = 49.47%（20.3 s），`progress` 为 1502/3000 = 50.07%——
比基线高 0.6 点，与 10 000 局口径的 +0.19 点同向，仍在 β 噪声内。


## PERF-18：复刻 Hill 的"按需加深"猜测（LARGE_ADAPTIVE_ANALYSIS）

Hill 仓库里那份 `hill-adaptive-ab` 的改动是：当全盘深搜因预算被跳过/没算完、只能回退成单格猜测时，
枚举至多 4 万张一致雷图，用同一个便宜的续局策略给"原选点"和候选打分；某个候选比原选点高
至少 0.5 个百分点才启用加深分析，并且**能证明**更优才改点。1 万盘同盘 A/B：54.75% → 54.83%，
+0.08 个百分点（95% 区间 −0.02 ~ +0.19），墙钟 +26%。

Python 版在 `minesweeper/solver/adaptive.py`（`guess_policy="adaptive"`），保留同样的"按需 + 必须证明"
结构，但为了 10 万盘量级把规模压到：未知格 ≤ 20、等权雷图 ≤ 256、搜索节点 ≤ 400，超出就放弃改点
（等价于 Hill 的"预算不足就不改"）。世界集合用大整数位集，分区/计数都是位运算。

201 主机、16×30/99、seed 2026、首点 (3,3)、10 万盘**同盘配对**：

| 策略 | 胜局 | 胜率 |
| --- | ---: | ---: |
| `min_prob` | 50,244 | 50.24% |
| `adaptive` | 50,231 | 50.23% |

两版都赢 50,177 盘、都输 49,702 盘；`adaptive` 单独赢 54 盘、`min_prob` 单独赢 67 盘，
**差 −13 盘（−0.01 个百分点），McNemar z = −1.18（不显著）**，耗时 143.7 秒。

改点确实发生了（两边不一致的 121 盘 ≈ 0.12%），但收益和损失基本抵消，方向还略偏负——
与 Hill 自己的 +0.08 个百分点（区间含 0）一致：**这个改进在他的求解器上是噪声级的，搬到我们这里同样是噪声级**。

为什么触发得少：我们大多数猜测发生在 unknown 45–99 的中盘，而等权雷图枚举在最坏情况下是
`C(空白格, 余雷)` 量级；Hill 能枚举 4 万张是因为他们用约束传播逐格展开（DFS），我们的
`endgame._worlds` 是"组件配置 × 空白格组合"，只能承受残局的规模。要把触发面做大，需要一个
带传播剪枝的世界枚举器，而不是调大上限。

## PERF-19：精确条件计数猜法（`informed`）——同盘 12 万局 +0.15 点

Codex 的评审文档（`新建 文本文档.md`）里最有价值的一条是：Hill 的求解器关掉全盘深搜后仍比我们高
1.75 点，靠的是**同风险候选的重排**（8,380 个猜测局面里约 72% 有并列最低候选）。本项目此前的
`progress` 猜法是这个思路的**采样版**（`rollout.choose_open_progress`：32 张雷图 × 4 个候选），
`docs/WINRATE_STRUCTURE.md` §2.1 提出把它换成**精确**条件计数。本轮就做这件事。

### 做法（`minesweeper/solver/informed.py`）

```
V(c) = Σ_k P(c 安全且翻出 k) · Q(条件于 k 之后)
```

* `P` 精确：`observation_distribution(system, c)` 用组件枚举 × 其余组件卷积 × 空白格超几何，
  直接给出"翻出 0..8 / 踩雷"的概率向量（不采样）；
* `Q` 一阶代理：把"格子安全且翻出 k"作为新约束加进系统（`conditional_system`），重算精确边际，
  取 `1 - min(table)` —— 即"下一手最安全的存活率"；
* 候选池 = 最低概率 + `band`（默认 2 个百分点）内、按 (概率, 坐标) 排序取前 5 个，
  谁 `V` 最大选谁；算不出来就退回 `min_prob`。

### 工程细节（都是踩出来的）

1. **预算必须收紧**：初版内部沿用原生加速器的 2000 万节点预算，20,000 局跑到 19,800 后卡了 6 分钟
   （个别局面每个候选要枚举几十秒）。改成 `DEFAULT_NODES = 200_000`、单次决策 `DEFAULT_TIME_LIMIT = 0.05 s`、
   每候选最多展开 6 个 ≥1% 的观测分支之后，20,000 局 67 s。
2. **`has_certainty -> 1.0` 是错的**：初版只要条件局面里出现 0/1 就把 Q 记成 1（"已经有确定格了"），
   但那些确定格常常只是几颗雷、下一手照样要赌。去掉这个捷径（Q 只依赖真实下一手风险）后
   20k 局从 +0.17 点变 +0.20 点，成本不变。
3. **带宽/候选数几乎没有影响**：`band=1e-9, candidates=8`（只比"完全并列"的候选）也是 +0.17 点，
   与 `band=0.02, candidates=5` 相同 —— 说明瓶颈不在"比多少候选"，而在 Q 的精度。

### 同盘 A/B（16×30/99，首点 (3,3)，201 主机，32 进程，配对 McNemar）

| 样本 | 基线 `min_prob` | `informed` | 差值 | z |
| 600（调试期） | 49.50% | 51.67% | +2.17 pt | 1.69 |
| 3,000（调试期） | 49.70% | 50.40% | +0.70 pt | 1.26 |
| 20,000 | 50.48% | 50.67% | +0.20 pt | 0.90 |
| 20,000（seed 9127） | — | — | +0.17 pt | 0.79 |
| 20,000（只比并列，band=1e-9） | 50.48% | 50.65% | +0.17 pt | 0.79 |
| **100,000** | **50.44%** | **50.59%** | **+0.14 pt** | **1.46** |

小样本的 +2 点是虚高（n=600 的标准误就有 ±2 点）；12 万局合起来是 **+0.14~0.20 点**，
合并后 p≈0.1，方向一致但幅度只有 Hill 那个 +1.75 的**十分之一**。

### 为什么只有十分之一

* 我们的 `Q` 只看"下一手"，Hill 的 `SecondarySafetyEvaluator` 会连着跑若干步（他说 4 个分支、
  采样占比 ≥15%），本质是"两拍"而不是"一拍"；
* 他的候选池是按他自己那套阈值（`SELECTION_THRESHOLD1 = 0.1`）划的，比我们的 band 宽；
* 本项目此前试过的两拍近似（PERF-4 `progress`）反而是负收益，说明"两拍"必须算准才有用，
  采样版不准就变成噪声。

### 结论

`informed` 留在 `--guess informed` 里作可选项，**默认仍是 `min_prob`**（+0.15 点没有超过
"换个默认策略"该有的置信度）。下一步若还想投入，方向是把这个 `Q` 从"一拍"升级成"精确两拍"
（条件系统里再递归一次同样的条件计数），成本约 4~6 倍，收益未知。

## PERF-20：最终版定稿——默认猜法改成 `progress`

### 为什么最终没有用 Hill 的 `LARGE_ADAPTIVE_ANALYSIS`

Codex 在 Hill 自己的发牌器上测到 54.83%（原版 54.75%），但那两个数字是 **Hill 的 Java 求解器 +
Hill 的发牌器 + JDK 21**；我们把等价的"按需加深"搬到 Python（`adaptive.py`，`--guess adaptive`）后，
在同一批盘上只有 50.51%（−0.01 点）——差异来自：

1. Hill 能枚举 4 万张**等权**一致雷图靠的是约束传播 DFS 剪枝，我们的 `endgame._worlds` 是
   "组件配置 × 空白格组合"，中盘就爆了，只能用 256 张世界；
2. 他的 54.83% 里本来就包含了"同风险候选重排"（我们这次实装的 `progress`）和整盘深搜两部分，
   其中"候选重排"在 Codex 的消融里值 **+1.75 点**，正是我们这次拿到的方向。
