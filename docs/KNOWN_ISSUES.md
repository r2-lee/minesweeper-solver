# 已知问题清单

本文件记录扫雷自动计算的算法缺陷、与旧版的行为差异，以及刻意保留的旧怪癖。

历史分两轮：

1. **拆分轮**（只搬结构、不改算法）：`KI-1`～`KI-6` 全部原样保留，只记录不修。
2. **修复轮**（`KI-1`～`KI-5` 已修）：假确定性、越界写入、贴边漏算等问题已消除，
   胜率见文末"胜率"一节；`KI-6` 属于"窗口裁边"的旧行为，保留但不再影响正确性。

## 已修复

### KI-1 `count == -1` 被当成有效结果（已修）

`Mat_Cal.Local_Mat_Cal` / `Whole_Mat_Cal` 在"根本没法算"时返回 `count = -1`
（C++ 里的提前返回），旧代码只判断 `count != 0`：

```python
# 旧版 minesweeper/solver/local.py
if count == 0:
    return {}
value = abs(acc / count)      # count == -1 时得到 0
```

后果：`abs(j / -1) == 0`，窗口里的格子被算成"必然安全（概率 0）"，自动计算径直踩雷。
这是旧版最致命的一个 bug：实测 40 局高级里有 2 局是"确定性动作踩雷"。

现在两处都改成 `count <= 0` 直接返回空表：

```python
# minesweeper/solver/local.py:57
if count <= 0:
    return {}
# minesweeper/solver/whole.py:44
if count <= 0:
    return {}
```

### KI-2 `min_x` 可能为负（已修）

```python
# minesweeper/solver/window.py
min_mines = board.mine_matrix[x][y] - board.adjacent_flags(x, y)
```

只要玩家在数字 `1` 周围标了 2 个雷（很常见的误标），`min_mines` 就是 `-1`，
而 C++ 里 `fill(selector.end() - x, ...)` 在 `x < 0` 时越界，属于未定义行为。

现在 `LocalSolver.probabilities` 先做范围检查，不合法就不调用原生模块：

```python
# minesweeper/solver/local.py:37
if window.min_mines < 0 or window.min_mines > window.max_mines:
    return {}
```

### KI-3 `Whole_Mat_Cal` 的 `x` 可能大于未开格数（已修）

`whole.py` 传的是 `board.remain_mine()`，它只按"已标雷数"算，不保证
`剩余雷数 <= 未开格数`；C++ 侧 `x > totalZeros` 同样越界。

```python
# minesweeper/solver/whole.py:33
if not unknown or remain < 0 or remain > len(unknown):
    return {}
```

### KI-4 `valid_coords` 的上界与切片上界不一致（已修）

```python
# 旧版
row_end = min(x + 1 + level, board.rows + 1)   # 谓词用 rows+1
for r in range(row_start, min(row_end, board.rows)):   # 切片用 rows
```

`_in_window(coord, start, end)` 要求 `min(coord+1, end) < end`，于是贴着下/右边界的
那一行/列会被判成"不在窗口内"，窗口实际比预期小一圈（3x3 的窗口会被裁成 2 行）。

现在裁剪和判定用同一个上界，并且按棋盘尺寸夹紧：

```python
# minesweeper/solver/window.py:143
def _in_window(coord: int, start: int, stop: int, size: int) -> bool
# minesweeper/solver/window.py
row_stop = min(x + 1 + level, board.rows)
col_stop = min(y + 1 + level, board.cols)
```

### KI-5 缺少 `i >= 0` / `j >= 0` 判断（已修）

旧版一维化时只做 `i - top` / `j - left` 平移，没有夹紧；`i < 0` 或 `j < 0` 时
Python 的负下标会从矩阵尾部回绕，`max_mines` 求和与 `strict_positions` 可能取到别的格。

```python
# minesweeper/solver/window.py:201
valid_rel = [
    (i, j)
    for (i, j) in valid_coords
    if 0 <= i - top < ax and 0 <= j - left < ay
]
```

### KI-7 局部窗口的雷数上界漏算边界数字格（已修）

旧版 `max_mines` 只累加"八邻域完整落在窗口内"的数字格，窗口边界上的数字格
眼睛看不到窗口外，它旁边的雷完全可能就藏在窗口里面，于是真实的雷数布局被排除在
枚举之外，候选格的累计值恒为 0，被当成"必然安全"。

真实对局里的例子（game 0，中心 `(15,29)`、level 2）：裁剪后矩阵
`[[1,2,0],[1,0,0],[1,0,1]]`，只有中心的 1 是 strict，旧公式得到 `max_mines = 1`，
而窗口里实际有 2 颗雷。直接问引擎（同一个矩阵、`strict=[8]`、`min=1`）：

```text
max=1        -> count=3, [(2,0),(4,-1),(5,-1),(7,-1)]      # (13,29) 平 2 的累计是 0 → 假安全
max=2 或 4   -> count=6, [(2,-3),(4,-2),(5,-2),(7,-2)]     # (13,29) 概率 0.5，正确
```

修复（`minesweeper/solver/window.py`）：

```python
# 和某个数字格相邻的雷，每颗至少被一个数字格数一次，而每个数字格最多数到
# 自己的值 -> 这类雷不超过矩阵里所有数字之和；完全不挨数字格的候选格最多全放满。
digit_sum = sum(trimmed[i][j] for i in range(ax) for j in range(ay) if trimmed[i][j] > 0)
max_mines = min(len(unopened_positions), digit_sum + isolated)
```

同时把 `unopened_positions` 从"只取 `valid_rel` 里的 0 格"改成"矩阵里所有 0 格"
——原生模块枚举的正是后者，漏掉边界候选格会让概率表少一项。

顺带修掉 `local.py` 里"窗口没有数字格 → 所有格必然安全"的推断（那只是没有约束，
不是没有雷）：现在返回 `{}`。代价可忽略：3 局真实对局 1591 个窗口里只有 94 个
上界变大，最大组合数 512，没有任何窗口超过 5 万。

回归测试：`tests/test_solver.py::WindowBoundsTest`（三个用例）。


### KI-6 `trim_zero_edges` 会连着裁掉多行全 0 边界

规则是"保留最内侧一行"，但当窗口底部连续两行都是 0 时会一起裁掉
（见 `tests/test_solver.py::LocalSolverTest::test_flagged_mine_makes_everything_safe`）。
这会让局部窗口比 `level` 期望的更小——旧版如此，且不会算错（窗口小只是约束少），
所以保留。它也是高级难度还可以继续优化的方向之一（现在默认走精确边际，这条路只有在
组件过大、退回窗口法时才会用到）。

### KI-8 边沿组件过大时会退回窗口法（装了原生加速器后不再发生）

精确边际要把"边沿"按连通性分解成组件、逐个枚举再用总雷数卷积。
极少数局面下整个边沿会连成一个 41~73 格的大组件，纯 Python 枚举需要
40 万~300 万节点（约 5 µs/节点，1.7~15.7 秒），于是 `FrontierSolver`
触发 `FrontierTooLarge`，`AutoSolver` 记一条 warning 后退回窗口法算这一步。

为什么会连成一大块：这些局面往往还剩 34~95 颗雷、74~410 个完全自由的空白格，
总雷数约束几乎剪不掉任何分支（组件雷数 k 的可行范围接近 `[0, 65]`），
而且加"强制赋值传播"只能把节点数减半、耗时不变（传播本身要扫全部约束）。

**纯 Python 实现下**的实测影响（Linux，seed 2026，2000 局高级）：

| 预算 | 退化次数 | 胜局 | 耗时 |
| --- | --- | --- | --- |
| 40 万节点（默认） | 60 次调用 / 12 局（0.6%） | 988 / 2000 = 49.40% | 48.1 s |
| 800 万节点 | 2 次调用 | 987 / 2000 = 49.35% | 81.1 s |

受影响的 12 局平均每局会连撞 5 次（大组件一旦形成，接下来几步都还是它）。
也就是说：把预算放大 20 倍、慢 69%，胜率反而**低 1 局**（噪声范围内），
而单次调用的最坏耗时会被拖到 8~15 秒——所以纯 Python 下刻意**不**追求"零退化"。

**现在**：`native/frontier_native.cpp` 把同一套枚举换成 C++（计数用 128 位整数，
结果逐位相同），同一批 19 个最坏组件从 1.7~15.7 秒降到 **8~64 ms**；
装了它之后预算自动放宽到 `NATIVE_BUDGET = 20_000_000`，实测 2000 局高级
**0 次退化**，基准耗时 48.1 s → 3.6 s（Linux）/ 152.6 s → 26.0 s（Windows 32 位）。
没有编译产物时仍然是上面那条纯 Python 路径，行为不变。

### PERF-1 同一格被多个窗口重复产出（已修，附记）

相邻的数字格会把同一批未开格各算一遍，旧版于是把同一格展开/标雷好几次
（对已展开格再展开是空转）。现在按当前棋盘状态跳过已展开/已标记的格子
（`minesweeper/solver/strategy.py:157`）。高级 100 局的动作数从 900+ 降到 241，
测量耗时从 40s 降到 34s，胜率不变。

## 刻意保留的旧版怪癖（不是 bug，但别当特性用）

* `ui/main_window.py` 的 `eventFilter` 里运算符优先级：
  `buttons == (Left|Right) or buttons == Middle and not isFinish`
  等价于 `(左右同按) or (中键 and 未结束)`，即**左右键同按不受 `isFinish` 保护**。
* `on_middle_button_clicked` 作弊分支里的 `if mark != 10`：标记只可能是 `0/1/2/-10`，
  条件恒真，等价于直接处理邻域。
* `SettingsDialog.get_settings()` 在"什么都没选"时返回 `{}`，调用方必须判空
  （`reinitialize_game({})` 直接返回）。
* `flood_open` 对已经展开的空白格不再扩散（旧版靠 `index_Matrix` 达到同样效果），
  所以对同一格重复展开只会返回它自己。
* `Board.is_won()` 的判定是"未展开 + 已标雷 的格子数 == 雷数"，
  也就是理论上允许"标错一个雷、同时漏掉一个雷"却判胜；实测 100 局里 43 次胜利
  全部是"真的把所有安全格都开完了"，所以没有实际影响。

## 原生模块的已知怪癖（接口层已注释）

* `local_mat_valid` 的 `inner_pos` 在 C++ 里是 `unordered_set<int>`，
  pybind11 **只接受 `set`**，传 `list` 会 `TypeError`；`NativeEngine` 已自动转换。
* `Local_Mat_Cal` 返回的 `result[i].first` 只有在"至少出现一个合法配置"时才被赋值，
  否则全是 `(0, 0)`。
* `Mat_Cal.pyd` 是 32 位，只有 `runtime\python.exe` 能导入。
* 原生模块本身没有对 `min_x < 0`、`x > totalZeros` 做防护（KI-2/KI-3 的根源），
  Python 侧现在会先挡掉这些输入。

```
runtime\python.exe tools\winrate_legacy.py -n 100                   # 与旧算法同一批雷图对比
```

`seed=2026`，同一批雷图上两种模式对照：

| 难度 | 窗口法 | 精确边际（默认） | 样本 |
| --- | --- | --- | --- |
| 初级 9x9 / 10 雷 | 95.8% | **96.3%** | 2000 |
| 中级 16x16 / 40 雷 | 84.9% | **87.3%** | 4000 |
| 高级 16x30 / 99 雷 | 42.5% | **51.3%** | 600（精确模式另测 1000 局为 49.9%） |

* 缺陷修复前，同一批 100 张高级雷图上只有 **33%**（33 胜 / 64 踩雷 / 3 局卡死）；
* 精确边际在 `solver/frontier.py`：边沿按连通性切成组件、每个组件枚举全部合法布雷、
  再用剩余雷数卷积，得到全盘每格的精确概率；预算 400k 枚举节点，超了打一行
  `warning` 退回窗口法（高级 1000 局里只触发 26 次）；
* 正确性：与暴力枚举逐格对照（400 张随机 4–5x5 盘）0 处不一致（`tests/test_frontier.py`）；
* **跨平台交叉验证**：Windows（32 位 Python 3.8 + 原生 `Mat_Cal`）与 Linux
  （Python 3.14，纯 `ReferenceEngine`）在同一 `seed` 下逐局结果完全相同；
* **样本量很重要**：初级 1000 局的分块胜场在 92~98 之间浮动，100–200 局的差异基本是
  噪声，比较算法至少 n≥1000。

继续提升的方向：

* 猜点时考虑"这一格能揭开多少"（一步 rollout）——理论上还能再提几个点，成本较高；
* 提高预算 / 改进枚举顺序，减少"组件过大"退回窗口法的次数（目前收益很小）；
* 初级已经贴着天花板：约 10% 的盘必须猜，其中约 6% 是精确 50/50。

## PERF-2：猜哪一格的一步前瞻（已实现、已实测、未采纳）

**问题**：现在（`min_prob`）遇到必须猜的局面，只挑"雷概率最低"的格子，等于只优化
"这一步别死"，没有考虑"打开之后能连锁定下多少格"。

**文献**：这个方法在文献里确实有，叫 one-step lookahead / educated guess：

* Couëtoux, Milone, Pellegrino, *Monte-Carlo Tree Search for the Game of Minesweeper*
  (INRIA RR-8041, 2012) 里明确说"只看一步的贪心"会被前瞻压制，它的 OH 变体就是对每个
  候选动作估计"观察之后的局面质量"。
  <https://inria.hal.science/hal-00723550v1/preview/RR-8041.pdf>
* minesweeper.info 的 *Minesweeper Constraint Satisfaction* 里有一节讲 educated guess，
  给了"估计概率 vs 实际成功率"的对照表。
  <https://minesweeper.info/articles/MinesweeperConstraintSatisfaction.pdf>
* 现成开源实现基本都是"最小概率 + 平局排序"，没找到可直接复用的前瞻选点代码：
  <https://github.com/GeorgeD88/Minesweeper-Solver>（Python/GPL）、
  <https://github.com/petersohn/mine-solver>、<https://github.com/aijobclub/minesweeper-solver>

**实现**：`minesweeper/solver/guess.py`，`SolverConfig.guess_policy` 可选
`"min_prob"`（默认）/`"lookahead"`。

* 对每个候选格，按精确边际**采样**若干张一致雷图；
* 在假设棋盘上真的把这一格开掉（含 0 格连锁），再把"确定能开的格"反复开到不动点；
* 收益 = 因此解掉的**边沿格**数量（远处空白格不算，它们不给约束）；
* 打分 `P(安全) × (1 + 收益)`，取最高者。

**实测**（高级 16x30/99，`seed=2026`，精确边际，n=2000，Linux，16 进程）：

| 策略 | 胜率 | 耗时 |
| --- | --- | --- |
| `min_prob`（默认） | **49.4%**（988 胜） | 31.6 s |
| `lookahead`，只在打平的候选里比 | 48.5%（970 胜） | 129.9 s |
| `lookahead`，在前 4 个最低概率里比 | 49.0%（981 胜） | 200.8 s |

结论：**在精确边际之上没有收益**（48.5%~49.0% vs 49.4%，且慢 4~6 倍），所以默认仍然是
`min_prob`，前瞻只作为可选项保留（`--guess lookahead`）。

为什么没用：

* 打到这个水平后，剩下的败局基本都是**精确 50/50**（每局平均 2.5 次猜测、每次致死概率
  均值 0.285），选哪一格不改变连乘的存活率；
* 我们的"收益"只是"能多确定几格"的代理指标，而文献里真正起作用的是对**胜率**的估计；
  把"开出来能连锁"当成收益，会让求解器偏好"风险略高但看起来信息多"的格子，实测更差；
* 采样器原来有偏（见下），修正后前瞻从 45.8% 回到 48.5%，说明之前那 3 个点的差距有一半
  是估计噪声。

**顺手修掉的采样偏差**：`sample_mines` 原来取 DFS 找到的**第一张**一致雷图，早期分支被
系统性偏爱——实测单格频率能偏 0.3。现在改成精确均匀抽样：先按组件枚举出的方案数做
卷积、从**精确后验**里抽"这个组件有几颗雷"，再逐个格子按"条件方案数"抽是不是雷；
`tests/test_guess.py::SamplesMatchMarginalsTest` 用 4000 次采样对照精确边际做回归。


## PERF-3：端局精确求解（已实现，收益未达预期）

**动机**：JSMinesweeper 的 *brute force analysis* 在"剩余方案数 <= 750"时把每一格、
每种顺序都推演一遍，直接算胜率；它自述这能让求解器走出（之一的）最优路线。我们的
"一步前瞻"用"能连锁定几格"当代理指标，实测没用（见 PERF-2），所以试试直接把胜率算出来。

**实现**（`minesweeper/solver/endgame.py`）：把局面展开成所有自洽的完整雷图（worlds），
在信念集合上做期望最大搜索——每个候选格按"开这一格会看到什么"把 worlds 分组，值 =
`Σ |组|/|总| × 子局面值`；`|worlds| == 1` 或安全格全开时值为 1。门槛由
`SolverConfig.endgame_cells/worlds/nodes`（默认 20/512/2000）控制，超了返回 `None`
退回启发式。观测（连锁展开结果）按 `(雷图, 格)` 缓存，单次求解约 32 ms。

**实测**（seed 2026，高级 16x30/99，n=2000，Linux 16 进程）：

| 配置 | 胜场 | 胜率 |
| --- | --- | --- |
| `endgame=False` | 988 / 2000 | 49.40% |
| `endgame=True`（默认） | 996 / 2000 | 49.80% |

* 端局求解只在 **18.5%** 的猜测里生效（604 次猜测、112 次命中）；返回的胜率估计
  mean 0.473 / min 0.167 / max 0.889。
* 生效比例低是因为大多数猜测发生在 unknown 45~99 的中盘，而端局门槛是 unknown <= 20。
* 命中部分的收益是 +8 局（+0.4 点），在 n=2000 的噪声范围内（σ≈1.1 点），
  也就是说"端局算得准"并没有转化成可测的胜率提升——真正决定胜负的是中盘那几次猜。

**结论**：保留实现（便宜、能给"这一格最后能赢的概率"这个数字），但不要指望它抬胜率；
公开最高分（JSMinesweeper 现代高级 54.3%）比我们高 4~5 点，差距更可能在它文档里写的
**猜测启发式**上：对"最安全格 10% 以内"的所有候选，混合 *progress percentage*（这一手
之后能不能立刻出现 100% 安全的动作）与 *secondary safety*（连这一手和下一手都活下来的
概率）。我们试过的"连锁定几格"只是 progress 的粗糙版本，没算 secondary safety。


## PERF-4：JSMinesweeper 式"进度猜法"（已实现，无收益）

**动机**：JSMinesweeper 的 README 说他们的猜法不是挑最安全的格，而是对"最安全格
10% 带宽内"的每个候选算两个量再混合：

* *progress percentage*——这一手之后能不能立刻出现 100% 安全的动作；
* *secondary safety*——连这一手和下一手都活下来的概率。

我们的 PERF-2（前瞻）只做了前者的粗糙版本，所以按他们的定义重写了一版。

**实现**（`minesweeper/solver/guess.py` 的 `choose_open_progress` / `secondary_safety`）：
先用无偏采样抽出若干张自洽雷图，对每个候选格按"开出来看到什么"把雷图分组，只保留
权重大于 15% 的最多 4 组；每组重建假设棋盘、用精确边际求下一手的概率表，取
`最高存活率` 与 `是否存在 0 概率格`；最后 `score = P(这格安全) × E[下一手最高存活率]`，
带宽 `p <= 0.1 + 0.9 * p_min`。用 `--guess progress` 打开。

**实测**（seed 2026，高级 16x30/99，n=2000，Linux 16 进程 + 原生加速器）：

| 猜法 | 胜场 | 胜率 | 耗时 |
| --- | --- | --- | --- |
| `min_prob`（默认） | 995 / 2000 | 49.75% | 4.0 s |
| `progress` | 996 / 2000 | 49.80% | 51.2 s |

**结论**：差 1 局、纯噪声，但慢了 **12.8 倍**。三次尝试（PERF-2 前瞻、平局比进度、
PERF-4 两拍存活率）都说明：在精确边际之上，"猜哪一格"的两拍近似无法超过
"挑最安全格"。原因大概是——决定胜负的是那个**无论如何都要付的硬币**，而两拍代理
只看到"下一手是否好过"，看不到"后面还有几枚硬币要付"；真要做对，就得 rollout/MCTS
（把整局玩完统计胜率），成本是秒级/次，不适合实时对局。

**顺带确认**：中心开局的 1000 局胜率是 **50.7%**，与 MinesweeperHQ 的 50.7%（10 万局）
完全一致；首点开出的面积和胜率没有明显相关（9 格的 54 局只有 40.7%，其余各档在
35%~77% 之间随样本波动）。


## PERF-5：边沿信念集合上的期望搜索（复现 EdLogg 的 "game tree" 猜法）

**动机**：EdLogg 的求解器（<https://github.com/EdLogg/MineSweeper>）在专家档公布
54.22%（v1.1、首点 3,3、每种子 10000 局）。用它的发牌器跑我们的求解器，同样的棋盘我们只有
51.28%（5000 局）——差的 3 个点在求解器一侧。它的 ReadMe 说猜法靠 Rule 5「Brute Force /
GameTree」：在解的数量有限时把后续整棵博弈树推演一遍，按"估算胜率"排序，并且
`threshold=0.96` 允许选略不安全但更有进展的格子。

**实现**（`minesweeper/solver/lookahead.py`）：把**边沿**展开成"世界"，每个世界的权重是
`C(空白格数, 余雷数)`（空白格对称、解析处理，所以中盘也能用）；然后对候选格按"开出来看到
什么数字"分组，`value = Σ 组权重/总权重 × 后续价值`，递归到深度上限。深度 1 精确退化为
`min_prob`。接入方式是 `SolverConfig.guess_policy = "search"`。

**A/B（同一批 EdLogg 棋盘，seed 1–5，高级 16x30/99，首点 (3,3)）**

| 猜法 | 胜场 | 胜率 | 耗时 |
| --- | --- | --- | --- |
| `min_prob`（默认） | 1009/2000 | **50.45%** | 3.8 s |
| `search` 深度 2 / 800 世界 | 1007/2000 | 50.35% | 7.0 s |
| `search` 深度 3 / 2000 世界 | 1004/2000 | 50.20% | 38.4 s |
| `search` 深度 8 / 800 世界 | 1004/2000 | 50.20% | 197.8 s |

**为什么没赚**：叶节点的价值假设"边沿清完 ≈ 赢"，但真实局面里空白格还藏着一堆雷
（中盘 remain 常常 40+），这个假设系统性乐观，于是搜索会为了"清边沿"去冒本不该冒的险。
把价值改成"还要再猜几次"又需要 rollout，成本就上去了——这正是 PERF-2/PERF-4 反复撞到的
同一堵墙：**在这套发牌器上，"挑最安全的格"本身非常强**，用近似的方式换"信息量"基本都亏。

**结论**：`search` 保留为可选项（`--guess search`），默认仍是 `min_prob`。要真正追上那 3 个点，
大概需要把 `endgame` 的**整局**博弈树（而不是深度截断）搬到边沿世界上——但端局门槛
（未知格 ≤20）挡着，中盘进不去，这条路还得再想办法。


## PERF-6：直接模拟"打开这一格能不能赢"（rollout 猜法）+ 端局门槛放宽

**动机**：把 PERF-5 留下的两个方向一次做完——(1) 猜法的价值不再用"清了几格"这种代理，
而是**真的把棋下完**再算胜率；(2) 把端局精确求解的门槛放宽，让它能进中盘。

**实现**
- `minesweeper/solver/rollout.py`：按后验抽若干张自洽雷图（`frontier.sample_mines`，无偏），
  对每个候选格 c 在每张雷图上"打开 c → 用基础策略（精确边际 + 最安全格 + 端局）下到终局"，
  胜率就是 c 的价值；候选取"最低概率 + `band` 以内"的前几个（默认 4 个、`band=0.25`、
  每格 3 张雷图）。接入方式是 `SolverConfig.guess_policy = "rollout"`。
- 端局门槛从"未知格 ≤20 / 512 世界 / 2000 节点"放宽到 **40 / 1500 / 4000**，让中盘的猜测也能吃到精确求解。

**A/B（高级 16x30/99，seed 2026，2000 局，Linux 16 进程，精确边际 + 原生加速器）**

| 配置 | 胜场 | 胜率 | 耗时 |
| --- | --- | --- | --- |
| `min_prob`（默认） | 995/2000 | 49.75% | 4.1 s |
| `rollout`（3 张雷图 × 4 候选） | 998/2000 | 49.90% | 14.3 s |
| `rollout`（12 张雷图 × 4 候选） | 999/2000 | 50.00% | 48.0 s |
| `min_prob` + 放宽端局门槛 | 996/2000 | 49.80% | 5.7 s |

四条都在 σ≈1.1 点的噪声内。rollout 把"连锁清场"的收益算进去了，但**没有转化成胜率**。

**为什么**：把两边的期望胜率拆开看就清楚了。它自己记录的 `prob`（每步存活率连乘的平均）是
**0.55**，我们是 **0.49**；但两边"每次冒险的平均风险"几乎一样（1 − 0.55^(1/2.27) ≈ 0.229
对 1 − 0.49^(1/2.76) ≈ 0.225），差别在**冒险次数**：它 2.27 次/局，我们 2.76 次/局。
也就是说，它的优势不是"选得更准"，而是**整局少冒 0.5 次险**——这是"先开哪一片能让后面
变成确定局面"的**全局规划**问题，一步 rollout 看到的只是"这一步之后还能活多久"，
在 2000 局的尺度上抵不过噪声（12 张样本的标准误约 0.14，而候选之间的差异往往只有 0.03~0.08）。

**结论**：`rollout` 保留为可选项（`--guess rollout`），默认仍是 `min_prob`；端局门槛保持
20/512/2000（放宽只会变慢）。想真正追上那 3 个点，需要的不是更好的单步评估，而是
**把"减少冒险次数"当成显式目标**的规划（例如按"开完这一格之后还剩几次必须猜"做搜索），
那已经是另一个量级的工程。

## PERF-7："少猜优先"猜法（按"打开后还要猜几次"排序，已实现、无可测收益）

**动机**：胜率近似 ``P ≈ q ** n``（``q`` 是每次冒险的平均存活率，实测约 0.775；
``n`` 是整局还要猜几次）。我们的 ``q`` 已经压到底（每步都挑最安全的格），和 EdLogg 的
差距几乎全在 ``n``：他 2.27 次/局、我们 2.69 次/局，``0.77 ** 2.27 ≈ 0.55`` 对
``0.77 ** 2.69 ≈ 0.50``——正好是两边的胜率差。所以"少猜一次"理论上值 +2~3 个点。

**实现**（`minesweeper/solver/guess.py`）：``choose_open_fewest`` 在"雷概率最低 + 带宽内"
的候选里，对每个候选假设打开它、连锁到不动点，然后用 ``frontier.build_system`` 重建约束、
``frontier.probabilities`` 数出"还有几个边沿组件没被钉死"，空白区按
``FREE_PER_GUESS = 40`` 折算，打分

    score(c) = (1 - p(c)) * FEWEST_Q ** n_after(c)        # FEWEST_Q = 0.775

这个量是**结构量**（整数、不靠采样胜负），本意是避开 rollout 那类 Bernoulli 噪声。

**实测（Linux，16 进程，seed 1–5 各 400 局 = 2000 局，EdLogg 发牌器，首点 (3,3)）**

| 猜法 | 胜场 | 胜率 | 猜测/局 |
|---|---|---|---|
| `min_prob`（默认） | 1009/2000 | 50.45% | 2.688 |
| `fewest` | 1015/2000 | **50.75%** | 2.643 |

差 6 局、0.3 个点，在 σ≈1.1 点的噪声内。放大候选带宽（0.25 → 1.0）结果**完全不变**，
说明决定性的不是带宽，而是下面这个缺陷。

**根因（关键）**：探针统计 100 局、1464 次候选评估——**1294 次（88%）返回 `None`**。
中盘的边沿组件常有 40~70 格，`probabilities()` 会抛 `FrontierTooLarge`，于是所有候选
都拿同一个兜底分数 ``survival × 0.775²``，排序退化成"挑概率最低"——**这个策略在
88% 的情况下等于没生效**。只有 12% 的评估（多半在残局）真的算出了 ``n_after``，
那点收益就是胜率上多出来的 6 局。

**为什么不能再修**：要数清"还剩几个组件要猜"就必须知道每个组件是否被总雷数钉死，
而这需要完整枚举——中盘 60 格的组件组合数是天文数字。也就是说，"精确数 n"只在残局
可算，而残局已经被 `endgame.py` 的精确求解覆盖了（PERF-3）。中盘想估 n，只能靠近似，
而近似（开出来多少格、组件还剩几个）正是 PERF-2/4/5/6 已经证伪的那一类代理。

**结论**：`fewest` 保留为可选项（`--guess fewest`，也接受 `fewest_band` / `fewest_worlds`
配置），默认仍是 `min_prob`。真正要吃掉那 3~5 个点，方向有两个：
1. **残局提前化**：把 `endgame.py` 的精确信念搜索提前到 unknown ≈ 30~40 就启用
   （现在门槛 20），代价是搜索规模，收益是"把要猜变成确定"；
2. **多步规划**：以"整局还要猜几次"为目标的搜索（不是单步代理），但那要在信念集合上
   做递归 DP，成本远高于当前的单步评估。

## PERF-8：超级位置（EdLogg 的 SUPERLOC）复刻，实测无收益

EdLogg 的求解器在"必须猜"时**不是**挑最安全的边沿格，而是挑一个"开出来能清掉一片"的
空白格（super location）。把他的控制台版跑 240 局统计每一步的规则，能直接看到这一点：

| 规则 | 次数/局 | 该步存活概率（均值） |
| --- | --- | --- |
| `RULE_1` 标雷 / `RULE_2` 展开 / `DEDUCE` | 110.1 / 72.7 / 14.7 | 1.000（都是确定动作） |
| `SUPERLOC` 超级位置 | **1.18** | **0.883** |
| `GAMETREE` 期望搜索 | 0.38 | 0.588 |
| `GUESS_0` 最低概率 | 0.36 | 0.506 |
| `GUESS_2` / `GUESS_1` 兜底 | 0.33 / 0.10 | 0.914 / 0.794 |

也就是说：他每局约 2.35 次猜测里，**一半是"88% 安全、但能炸开一片"的空白格**，纯 50/50
只有 0.36 次；我们 2.69 次猜测里 0.44 次是 50/50。胜率差 3 个点，几乎全部来自
"少 0.08 次硬币"。

复刻了两种打分，A/B 都是 2000 局高级（EdLogg 发牌器、seed 1–5、首点 (3,3)）：

| 打分 | 胜率 |
| --- | --- |
| 基线 `min_prob` | **50.45%** |
| `(1-p) × 区域大小`（直接按面积） | 47.80% |
| `region × safety^(region+1)`（照抄他的 `count * openProb[count+1]` 形状） | 50.40% |
| 同上但把带宽放到 0.25 | 50.20% |

结论：他的"冒一点险换清场"在他自己的规则组合里成立，但**单独搬到我们这里不成立**——
我们的精确边际已经会在空白格更安全时自动选它，硬去优先空白格只是多冒险。`superloc`
留作可选项（`--guess superloc`），默认仍是 `min_prob`。

## PERF-9：完整期望搜索（EdLogg 的 GAMETREE）与"直跳空白区"，实测仍无收益

PERF-8 之后还剩两个没验证的机制，这轮都做了：

**1. `gametree`（`minesweeper/solver/gametree.py`）** — 与 `lookahead` 的差别只在
"不截断"：状态是 (还活着的世界下标, 已经点开的边沿格)，一路递归到**边沿清空**，叶节点
用"剩余雷按密度均摊到空白区"的解析值收尾（`BLANK_REGION = 40`）。这样它算的是"这盘真
赢下来的概率"，而不是"清完边沿就赢"的乐观估计。

| 配置（高级 16x30/99，EdLogg 发牌器，seed 1–5 各 400，共 2000 局） | 胜率 | 耗时 |
| --- | --- | --- |
| `min_prob` | **50.45%** | 4.4 s |
| `gametree` | 50.85% | 62.2 s |

+8 局（+0.4 点），σ≈1.1，仍在噪声内；慢 14 倍。

**2. `blank`（直跳空白区，`choose_open_blank`）** — 完全照他的形状：候选只有"不挨着
任何已开格"的空白格，按 `safety × (1 + min(空区大小, 8))` 打分，再和"最安全边沿格"直接
比，谁大选谁。**结果 40.90%**（1000 局），比基线低 10 个点——不设概率带宽就往空白区跳，
是在送死。

**决定性实验：把他的 GAMETREE 关掉**
给 `ed.exe` 加了 `ED_MAXSOL` 环境变量（`maxSolutions = 0` 时 `UseGameTree` 直接返回
false），他的发牌器 seed 1、2000 局：

| | 胜率 | 猜测/局 |
| --- | --- | --- |
| 默认（`maxSolutions = 1000`） | 53.75% | 2.24 |
| 关掉 gametree（`maxSolutions = 0`） | **54.00%** | 2.29 |

也就是说：**他的 game tree 对他自己的胜率贡献约等于 0**。这条把"差距 = 端局精确搜索"
的可能性也排除了——我们先后复刻的九种机制（前瞻、进度、两拍存活、边沿期望搜索、
rollout、少猜优先、超级位置、完整期望搜索、直跳空白区）没有一种能补上这 3 个点。

结论：差距不来自"某一条猜法规则"，而来自**整局的猜测序列规划**（他的 2.24 次/局 vs
我们的 2.69 次/局是结果、不是原因）。要真正追平只能做"以最终胜率为目标的多步规划"，
代价是几个数量级的算力；当前的 `min_prob` 在"单步最优"这一层已经到顶。

## PERF-10：把"每步重建整盘"的开销压下去（胜率不变，速度 2.25 倍）

`perf` 这一路一直是"想赢棋"，这一节反过来：**在不动策略的前提下**把单局耗时降下来。
动机很直接——同一台机器上 EdLogg 的 C++ 求解器约 4 ms/局，我们当时约 144 ms/局，
差 35 倍；即使胜率追不上，"每局要花多久"本身也是可验证的指标。

剖析（40 局高级、单进程）指出的热点与处理：

| 热点 | 占比 | 改法 |
| --- | --- | --- |
| `Board.is_won()` | 40% | 生成器逐格判断 → 逐行 `list.count(Mark.COVERED) + count(Mark.FLAG)`（C 层循环） |
| `frontier.build_system()` | 18% | 内层 `neighbours()` 生成器 → 显式八邻域展开；**保持 `DIRECTIONS` 顺序**（换顺序会改变并列时的选择，实测会改变胜负） |
| `math.comb` | 10% | 卷积里同一个 `(自由格数, 剩余雷数)` 反复求值 → `lru_cache` 记忆化 |
| `board_values()` 重复计算 | 6% | `FrontierSolver.probabilities(values=...)` 接收调用方已经算好的值数组 |

结果（同一批棋盘、胜负逐局一致）：

| | 改前 | 改后 |
| --- | --- | --- |
| 400 局高级，单进程（Windows） | 58.11 s | **25.83 s** |
| 2000 局高级，16 进程（Linux） | 4.3 s | **2.8 s** |
| 胜负 | 215/400、1009/2000 | 完全相同 |

一条踩坑记录：`build_system` 里把邻居顺序从 `DIRECTIONS` 换成"行列扫描"后，223 个
测试里有 1 个失败、400 局胜场从 215 变成 213——因为并列最低概率时取的是"第一个"，
顺序变了走子就变了。**性能改动也必须逐局比对胜负，不能只看测试是否全绿。**

## PERF-11（已撤回的结论）：逐决策重放为什么不可靠

早前用 `tools/replay_trace.py` 把 EdLogg 的 `Expose`/`AddMine` 调用重放到我们棋盘上，
得到过"他的猜点从不比我们更安全（0/671）"这个结论。复查发现**这个结论不能成立**：

- 他的 `AddMine` 不只在"真标雷"时被调用（`tank.cpp:1509/1526` 的推断路径也会调），
  实测每局约 560 次、其中约 70% 落在安全格上——把这类调用当成"他标了这些雷"会得出
  自相矛盾的棋盘；
- 用 trace 里的 `end` 行还原雷图后，`(3,3)` 周围 3×3 并不总是无雷，说明重放出来的
  中间状态和他的真实状态并不一致。

所以那句话要撤回：**我们只确证了"每局猜测次数"这一点（他 2.24~2.40 次、我们 2.7~3.2
次），没有确证"他的猜点更差"**。逐决策对比要成立，得在他的求解器里直接打出决策时刻的
状态（而不是事后从底层调用反推），这条线这次没走完。

## PERF-12：把"他为什么少猜"量化之后 —— 空白区赌博仍然不赚

**背景**：EdLogg 在同一批发牌器生成的棋盘上是 53.18%（5000 局复现），我们是 50.45%（2000 局）。此前一直拿"猜测次数"（他 2.27/局、我们 2.7/局）当差距解释，但那个口径不可比。

**裁判方法**：改造他的控制台探针，记录每个 `MakeMove()` 前后 `exposed[][]` 的真实差分，再把这些差分重放到我们自己的 `Board` 上。校验结果：用我们的数字重算他的 `exposed`，**44,610 次比较 0 处不一致**——他的决策时刻状态可以被精确复现。在这个状态上用 `frontier` 算精确边际，再拿真雷图核对，**1028 条"安全"断言、124 条"是雷"断言，0 错判**。

**发现（口径翻转）**：在他的 46 个干净猜测步里，他第一次实际动手的格子中

| 我们的精确模型判定 | 次数 |
|---|---|
| 可证明是雷（他直接标掉） | 21 |
| 可证明安全（他直接开掉） | 10 |
| 真正无法确定 | **15** |

他的概率模型是"每个周长列表各算各的"，缺跨组件 × 总雷数的联合约束，所以这些格在他看来有风险、于是既计入 `guesses`、又几乎不会死。按同一裁判口径：

| 指标 | 我们 | EdLogg |
|---|---|---|
| 每局步数 | 297.7 | 187.9 |
| 每局**真正无法确定**的决策 | **2.47** | **0.93** |
| 这些决策的平均雷概率 | 0.193 | 0.22 |

也就是说：**每一次冒险的风险我们并不比他差（0.193 vs 0.22），差的是次数（2.47 vs 0.93）**。他每局很早就用一次空白区的大赌（superloc，1.18 次/局）把大片未知翻成确定信息，之后基本靠推理走完；我们是一格一格磨边沿，磨到没确定格了再猜，赌的次数被拖到 2.5 次。

**本轮实验（`guess_policy="gamble"`）**：不再用"能连锁几格"这类代理，而是用 rollout 直接比较两个候选的整局模拟胜率——候选 A = 当前最安全的边沿格，候选 B = 最大空区里的一格（`rollout.blank_cell`，要求空区 ≥ `gamble_region_min`）；只有 B 的模拟胜率**严格更高**时才改选，否则原样走 `min_prob`。

A/B（他的发牌器，seed 1–5 各 400 局 = 2000 局，首点 (3,3)，Linux 16 进程，精确边际 + 原生加速器）：

| 猜法 | 胜场 | 胜率 | 耗时 |
|---|---|---|---|
| `min_prob`（默认） | 1009/2000 | **50.45%** | 2.8 s |
| `gamble`（2 样本 × 2 候选） | 1008/2000 | 50.40% | 6.8 s |

差 1 局，仍然是噪声。`gamble` 保留为可选项（默认 `min_prob`）。

**结论**：到这里为止，单步决策层面的十一种猜法（前瞻、两拍存活率、边沿期望搜索、rollout、少猜优先、超级位置、完整期望搜索、直跳空白区、deep 并列、gamble）全部没有超过"挑最安全的格"。剩下的唯一杠杆是**减少每局需要冒险的次数**，而那需要跨越多个回合的规划（信念集合上的多步搜索），不是单步打分能替代的。

### 附：PERF-12 的自我更正（同轮补充测量）

上面那张"我们 2.47 次 / 他 0.93 次"的表**不可靠，已作废**。它只统计了他 93 个猜测步里"总雷数对得上"的 37 个（过滤掉了 56 个），过滤标准本身没有查清。

换成不依赖雷数记账的口径：在他 30 局里，对**每一个**有实际动作的步都算一次我们的精确表，统计"整张表里没有任何 0 或 1"的状态数——他每局会遇到 **4.1 个**这样的状态（分布 `[8,2,4,3,3,4,4,4,4,6,2,3,1,3,7,8,2,5,4,2,4,2,3,2,8,1,10,8,3,3]`）。

也就是说：**他面对的"完全无法推理"的局面并不比我们少**（我们每局猜 2.47 次）。此前"他每局只冒险 0.93 次"的结论是小样本 + 过滤偏差的产物，撤回。

同时，"放宽端局门槛能减少猜测次数"也被证伪：

| 端局门槛 | 胜率 | 猜测/局 | 步数/局 | 耗时 |
|---|---|---|---|---|
| unknown ≤ 20 / 512 世界 / 2000 节点（默认） | 47.00%（141/300） | 2.62 | 277.4 | 3.5 s |
| unknown ≤ 40 / 4096 世界 / 20000 节点 | 46.33%（139/300） | 2.61 | 277.3 | 23.7 s |

放宽 6.8 倍代价，猜测次数几乎不动（2.62 → 2.61）——端局搜索只改变"猜哪一格"，不改变"要不要猜"。`tools/probe_guesses.py` 就是这条测量的脚本，留着供以后回归用。

## PERF-13：动作粒度 —— 他一次动作平均揭开 1.57 格，我们 1.23 格

只看**赢的局**（消掉"输得早所以开得少"的偏差），用他的 trace 和我们的逐步记录对齐同一个口径（一个"动作"= 一次 `MakeMove` / 一次 `Action`）：

| 指标 | 我们（31 局） | EdLogg（14 局） |
|---|---|---|
| 每局动作数 | 311.7 | 221.8 |
| 每次动作揭开格数 | 1.23 | 1.57 |
| 揭开多格的动作为占比 | **4%** | **22%** |
| 揭开 50% 格子所需动作 | 145 | 89 |
| 揭开 90% 格子所需动作 | 272 | 188 |

差距不在"每步判断得对不对"，而在**一次动作的信息吞吐**：他有 22% 的动作会连锁揭开多格，我们只有 4%。

原因从他的源码可以直接读到：他的 `MakeMove()` 里 RULE_2 是"这个数字的雷已标全 → 把剩下所有邻格一次全开"，所以一个动作会打开一整批格子；我们的 `Action` 是"一格一个动作"，`expansion` 只有碰到 0 格才连锁。这不改变"决策正确性"，但改变了两件事：

1. 我们的动作数是对手的 1.4 倍（311.7 vs 221.8），每一步都重新建约束、重算边际；
2. 更关键的是**顺序**：他一次把一片开完，下一轮推理拿到的信息更多；我们一格一格开，等于在信息不完整的状态里多做了很多次"重新推理"。

这一条目前还没被证伪，是最后一个可以做的结构改动。

## PERF-14：钉死组件搜索（他 UseGameTree 早跑分支）+ 概率标定审计

| 宽端局（40 / 4096 世界 / 20000 节点） | 50.50%（1010/2000） | 21.7 s |

**二、"钉死组件搜索"（`guess_policy="pinned"`，他的 `gametreeUsedEarly` 对应物）**

只对"雷数已被总雷数约束钉死"的连通组件单独做信念集合期望搜索（组件内枚举配置、`free=[]`、`total_mines=k`），返回价值最高的动作；没有钉死组件时退回 `min_prob`。

**三、概率标定审计（排除了"模型算错"这个可能）**

|---|---|---|
| ~0.0 | 20 | 0.050 |
| ~0.1 | 146 | 0.110 |

| ~0.4–0.5 | 47 | 0.489 |
| **整体** | 273 | **0.2015（预测 0.1841）** |

标定偏差 9%（n=273 的标准误约 2.4%），属于轻微保守；**0/1 判定此前已用 1028 条真值核对过零错判**。所以差距不是"概率算错了"。

## 方案二：我们的"确定性集合"是否等于全局闭包（结论：相等，无需移植）

**问题**：EdLogg 用 `ForceMine`/`ForceExpose`（`fastSolve.cpp`）做强制赋值传播来挖出"确定格"。我们的精确边际是否已经覆盖同样的确定性？如果我们的确定性集合更小，那才是可复刻的差距。

**方法**：构造可达局面（矩形未知块 + 其余全开，且不允许"0 数字的已开格挨着未知格"——这种局面真实对局中不可能出现，`flood_open` 会把它们一起翻开），用 `frontier.probabilities` 算精确边际，再用 `itertools.combinations` 暴力枚举全部自洽布局算真实边际，逐格比对。

**结果**：152 个可达局面、814 个格子，**0 处不一致**；另一次 51 局面 / 254 格同样 0 处。已固化为 `tests/test_frontier.py::ReachableExactnessTest`（25 个局面，跑在 `run_tests.py` 里）。

**结论**：精确边际对每个格子给出的概率就是完整约束系统（含总雷数）下的真实后验。因此凡是我们表里出现 0 或 1 的格子，都是**逻辑必然**；而他的 `ForceMine`/`ForceExpose` 只在单个周长列表内部做区间推导，推出的每一格我们也会有。也就是说：**他的确定性集合是我们的子集，移植传播不会多挖出任何一格**。这也与另一项实测吻合——把他自己的 `maxSolutions` 关掉（同时停用 gametree 与端局暴力），他的胜率从 53.75% 变成 54.00%（2000 局），说明那套深搜机器对他自己的收益约等于零。

**两次坏探针的教训**（都记在这里，避免再犯）：
1. `frontier.probabilities(system, budget=None)` 收的是 `ConstraintSystem`，不是 `Board`；传错类型会得到空表而不是异常，于是"全错"看起来像求解器崩了。
2. 用手工置 `Mark.OPENED` 造状态会造出不可达局面（数字 0 的格子旁边还盖着牌）。`build_system` 不为 0 格的邻居建约束是**正确的**（现实中它们必定已开），所以这类输入会得出"我们漏算"的假象。造测试局面必须用 `expansion` 或显式保证可达性。

## 同一裁判下的猜测口径（`tools/referee_guesses.py`）

两边各自数 `guesses` 口径不同，所以用**我们自己的精确表**当裁判，重放 EdLogg 的每一步（`d` 差分行），在他的每个"猜测步"上判断那一格在我们表里是 0、1 还是介于两者之间。40 局同盘结果：

| | 计数口径 | 裁判口径 |
| EdLogg | 2.15 次/局 | **1.82 次/局**（其中 ~0.33 次按我们的表是可证明的，其余为真正的猜测） |
| 我们 | 3.20 次/局 | 3.20 次/局（我们的猜测按构造必然是"无确定解"时的决策） |

同一批 40 局的胜率：我们 27/40 (67.5%)，他 26/40 (65.0%)（n=40，±7.5%，不能与 2000 局的 50.45% vs 53.18% 直接比）。

结论：他"少猜"是真的（1.4 次/局），不是计数口径造成的；真正的猜测风险两边接近（裁判口径下他 0.171，我们约 0.19）。但在这 40 局样本上我们的胜率并不落后，说明"猜测次数"与"胜率"之间的换算不是简单的 `q**n`，需要更大样本 + 记录"第一次真正猜测发生在还剩多少格时"才能继续定位。

之前的 2000 局对照（我们 50.45% vs EdLogg 53.18%）用的是 `tools/compare_edlogg.py` 里**我们自己用 Python 重写的发牌器**（`edlogg_layouts`）。这轮改用 `ed.exe trace` 的 `end` 行拿**他真实跑出来的雷图**，两边喂同一张盘，1000 局：

| | 胜局 | 胜率 | 猜测/局 |
| EdLogg | 524/1000 | **52.40%** | 计数 2.17 / 裁判口径 **1.71** |
| 我们 | 515/1000 | **51.50%** | **2.61** |

对照实验（同一套代码，只换雷图来源）：用 `edlogg_layouts` 生成的 500 张盘，我们 **50.40%**（与旧的 50.45% 一致）；用 trace 出来的 1000 张盘，我们 **51.50%**。→ 差异来自**雷图来源**，不是求解器：我们的 Python 重写发牌器与他的 exe 在种子链上并不完全一致（单盘核对过 seed 1 相同，但成批不同）。
